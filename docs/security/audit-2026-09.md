# Security audit, September 2026

TTP's first end-to-end security audit. It was run with [cloudflare/security-audit-skill](https://github.com/cloudflare/security-audit-skill) driving Claude Opus 5, against commit `1c794ca` on 18-20 September 2026, and every fix it produced ships in **0.4.9**.

This document is the honest version. It lists what was confirmed, what was **disproved**, and what is still open. The disproved section is not padding: most of the seven candidates that did not survive were rejected because a claim in them was factually wrong, and recording why keeps those hypotheses from being reopened.

## How it was run

Hunting agents proposed candidate defects. Each candidate then went to a **separate verifier with no stake in it**, instructed to re-derive every load-bearing claim from source, to actively hunt for evidence that would refute it, and to re-derive severity itself rather than inherit the proposal. A candidate became a finding only if its verifier personally reproduced or proved it.

That second pass changed the result substantially:

| | count |
|---|---|
| candidates proposed | 24 |
| confirmed as findings | **16** |
| disproved and rejected | **7** |
| still unresolved | 1 |

Four confirmed findings were **downgraded** by their verifier, and in two cases the verifier rejected the proposed *fix* as worse than the bug. Those are called out below.

### Execution boundary

No agent ever ran TTP with privilege. Source review was read-only; anything executed ran under `bwrap --unshare-all --clearenv` with no root and no network, and never invoked the real `nft`, `ip`, `systemctl`, `mount`, `semanage`, `tor` or `systemd-run`. Several questions that looked like they needed a live host were settled instead by reading documentation or inspecting shipped binaries read-only — see *Method notes* at the end.

### The five high-severity findings

#### 1. The account TTP treats as "Tor" was decided by a name

Two separate code paths picked the Tor account from something an unprivileged
local user controls.

In managed mode, `_detect_tor_user()` returned the owner of the first `ps` row
whose `comm` field was exactly `tor`. The kernel sets `comm` from the basename
of the file passed to `execve`, so `cp /bin/sleep ~/tor && ~/tor 600 &` is
enough to claim it. (`exec -a tor` is *not* — that changes `argv[0]`, and `ps`
reports `comm`.)

In `--external-daemon` mode, `_resolve_external_tor_uid()` asked which UID was
listening on the TransPort and accepted it whenever `"tor" in username.lower()`
— which is true of `victor`, `actor`, `contractor`, `mentor`, `factory` and
`history`.

The account is not cosmetic. It becomes the torrc `User` directive the real Tor
binary obeys, the target of root's `chown` of `/run/tor/ttp` (which holds the
ControlSocket and auth cookie) and `/var/lib/tor/ttp`, and the UID the firewall
exempts from **both** the NAT redirect and the fail-closed filter chain.

**Fixed** by binding detection to the trusted binary — a `ps` row is believed
only when `/proc/<pid>/exe` resolves to the same path `resolve_optional("tor")`
returns — by matching BYOD account names exactly, and by refusing any account
that is not a dedicated system account before it reaches those three sinks.

#### 2. Root wrote into a directory it had given away

`ensure_runtime_dir()` chowned all of `/run/ttp` to the unprivileged
`ttp-watchdog` account whenever that account existed — which every shipped
installer creates. The directory has no sticky bit, so its owner could unlink
any entry it did not own and replace it with a symlink, while root kept
creating and reopening files there by fixed name.

Three sinks were reachable that way, each confirmed separately:

- **`/run/ttp/resolv.conf`** — `Path.write_text` with no `O_NOFOLLOW`, then
  `mount --bind` on the same path *string*. The write truncated and overwrote
  an arbitrary file as root; re-pointing the link between the two steps
  published an attacker-owned inode at `/etc/resolv.conf`, where `search` and
  `options` directives the watchdog's nameserver-only check never inspects
  would steer every single-label lookup. No race was even needed for the write:
  teardown unlinks the file, so the name is free between sessions.
- **`/run/ttp/ttp.rules`** — written by path, then reopened by name by `nft -f`.
  Two independent path resolutions.
- **`/run/ttp/ttp.log`** — `exists()` then `open(O_CREAT)`-or-`chmod`, a
  check-then-act giving root-privileged file creation, a `chmod 0600` of an
  arbitrary file (which also strips setuid bits), and an append.

**Fixed** at the root cause — `/run/ttp` stays root-owned, the watchdog gets
group read and its own subdirectory — *and* at each sink independently, so
neither fix depends on the other. The ruleset now goes to `nft` on stdin; the
resolv.conf write is pinned to one `O_NOFOLLOW` descriptor and handed to
`mount` as `/proc/self/fd/<n>`; the log is opened once with `O_NOFOLLOW` and
validated with `fstat`.

This also unblocked the watchdog, which could not read the lock it was
monitoring: the file was `0600 root:root` while only the directory had been
handed over.

#### 3. A lock field became an extra `nft` command

`apply_teardown_lockdown()` formatted the session lock's `tor_uid` into an
`nft` argv with a bare `str()`, and `do_stop()` preferred any non-`None` lock
value over the lookups that produce a real integer.

`nft` joins its non-option arguments into a single buffer and lexes it
line-wise — established by disassembling the shipped binary, not by running it.
So `tor_uid = "0\ninsert rule inet ttp filter_out accept #"` made root insert
an `accept` at the top of `filter_out` during `ttp stop`, defeating the
redirect and the killswitch, in cleartext — while the surrounding
`except Exception` logged the teardown as successful.

**Fixed** by proving the value is a plain non-negative integer before it is
formatted in, and by falling through to the real lookups when it is not.

## Disproved candidates

Each of these was proposed as a defect and **did not survive** independent
verification. Recorded with the reason, so they are not reopened.

- **Installer `umask` hardening** — The premise was backwards. `sudoers(5)`
  documents the `umask` setting as defaulting to `0022`, and because
  `umask_override` is off by default the effective umask is the *union* of the
  caller's and that value: *"this guarantees that sudo never lowers the umask
  when running a command"*. A caller umask of `000` arrives as `0022`. Two of
  the three claimed sinks also do not exist — `packaging/ttp.service` runs
  `/usr/bin/ttp`, not `/opt/ttp/venv/bin/ttp`, and the source installer ships no
  unit file at all. And `mkdir -p` cannot change an existing directory's mode,
  so only a first-ever source install on a host that never had the RPM is even
  in scope.
- **SELinux `unreserved_port_t` over-grant** — The opposite of the claim. The
  loaded Fedora policy was queried read-only: the *only* `name_bind` grant
  reaching `tor_port_t` is for `tcp_socket`, and **no rule in the entire policy**
  grants any domain `tor_port_t:udp_socket name_bind`. So the disputed module
  line is not redundant for the UDP DNSPort — it is the only rule covering it,
  and deleting it as proposed would be a functional regression. (This turned up
  a *different* defect, listed under follow-up work.)
- **`ttp bypass` accepting `SUDO_UID=0`** — No boundary crossed. `sudo` sets
  `SUDO_UID` from the *invoking* user, so `sudo -i` from uid 1000 carries
  `SUDO_UID=1000`, not 0, and an injected `0` from a non-root user is
  overwritten before TTP sees it. The value can only be `0` if root itself
  produced it. Nothing in the repository lets a lower-trust principal reach the
  command.
- **`--restore-only` leaving a SELinux port label** — The residue points the
  other way. Ports are constrained to 1024-65535, whose default type is the
  generic `unreserved_port_t`, bindable by every confined domain holding
  `corenet_tcp_bind_all_unreserved_ports`; `tor_port_t` is bindable by far
  fewer. Leaving the label **narrows** who may bind the port.
- **Control socket group permissions** — Unreachable. `/run/tor/ttp` is
  `chmod 0700` unconditionally before every Tor start, and POSIX requires search
  permission on every path component. Tor never widens it either: the options
  affect the leaf socket and cookie only, and absent `RelaxDirModeCheck` (never
  set) Tor *insists* the directory be read-restricted.
- **Lock-write race** — Real and reproducible, but a reliability bug between two
  equally-privileged root invocations. All three proposed security framings were
  disproved in source: there is one volatile `ttp-tor.service` and start uses
  `systemctl restart`, so no second daemon is stranded; `apply_dns` clears prior
  overlays before mounting, so they do not stack; and the two racers derive
  identical DNS backups. The corrupt locks it produces land fail-*closed*.
- **Secret-scan coverage** — Prospective only. A far broader scan of all 195
  tracked files **and all 52 commits** found no credential, so there is no
  affected resource. Listed under hardening instead.

## Still unresolved

**The root-run shell scripts resolve privileged binaries through `$PATH`.**

`scripts/install.sh`, `scripts/uninstall.sh` and `scripts/restore-network.sh`
all require EUID 0 and are documented as `sudo ./scripts/<name>.sh`. None of
them assigns `PATH` or sets `set -euo pipefail`, and it is not only the
`command -v` guards — the real invocations are bare names too: `semodule -i` at
`install.sh:98`, `nft delete table` at `restore-network.sh:35`, `semanage port -d`,
`resolvectl revert`.

`ttp/paths.py` exists to forbid exactly this for the Python runtime, and its
docstring names the threat as *"a local privilege escalation"*. It also declines,
in writing, to rely on the control that would mitigate it: *"sudo usually blunts
this with `secure_path`, but 'usually' is not a security property: it is a
distribution default that an administrator can disable and that is not enabled
everywhere TTP supports."* The repository's own anti-`$PATH` lint
(`ruff --select S607`) is scoped to the `ttp` package, so `scripts/` sits
outside the project's own guard.

**Why it is not confirmed.** Whether `Defaults secure_path` is in force for the
documented route could not be observed — `/etc/sudoers` is `0440 root:root` and
`sudo -l` was outside the execution boundary — and **no invocation route inside
the repository bypasses sudo**: no Makefile target, CI job, container build or
package scriptlet runs these scripts. Without that, root executing an
attacker-chosen binary is not demonstrable from source.

**How to settle it.** On each supported platform, read `/etc/sudoers` and
`/etc/sudoers.d/*` for `Defaults secure_path`, then `ls -ld` every directory it
names — paying attention to `/usr/local/sbin` and `/usr/local/bin`, which the
Debian-family value places *ahead* of `/usr/sbin` and which `ttp/paths.py`
deliberately searches last and ownership-checks.

**Or make the question moot**, which is the better answer: give each script a
fixed root-owned lookup mirroring `TRUSTED_DIRS`, used for every guard *and*
every invocation, plus `set -euo pipefail`. That removes the dependency on
`secure_path` on every distribution. Tracked below.

## Known follow-up work

Deliberately **not** done in 0.4.9, with the reason:

- **`read_lock()` does not enforce a field-level schema.** Making it raise on a corrupt lock changes the contract of 23 call sites, and the raise would land between `destroy_rules()` and `delete_lock()` on the `--restore-only` path. 0.4.9 instead makes teardown survive a malformed lock; the schema itself is follow-up.
  Coercing bad fields to defaults was considered and **rejected**: `tor_uid` and `transport_port` drive privileged teardown actions, so a default would turn a loud crash into a silently wrong one.
- **`verify_tor()` conflates two different failures.** "check.torproject.org says you are not on Tor" and "check.torproject.org could not be reached" both render as *Traffic is NOT reaching Tor*, and set `has_leaks` in `check-leak`, even when a fallback reflector demonstrably answered through a working exit. The durable shape is a tri-state verdict.
- **`label_ports_selinux` uses the wrong target type for the UDP DNSPort.** Verification found that the loaded Fedora policy has **no** `tor_port_t:udp_socket name_bind` rule for any domain, so relabelling the DNS port to `tor_port_t` removes the one type (`unreserved_port_t`) that permitted the bind. This was discovered while disproving a different candidate and has not been validated end to end on a live enforcing host.
- **`do_stop()` skips SELinux unlabelling whenever `external_daemon` is set**, and `stop --restore-only` with no readable lock leaves stale port labels. Configuration drift rather than a weakening — the stale label is *more* restrictive than the default.
- **Shell installers resolve privileged tools through `$PATH`.** `ttp/paths.py` exists precisely to refuse that for the Python runtime, and its docstring declines to rely on sudo's `secure_path` because it "is not a security property". The same guard is not applied in `scripts/`, and the repository's own anti-`$PATH` lint is scoped to the `ttp` package. See *Still unresolved* above.

## Hardening noted but not treated as findings

- `make lint-secrets` matches five vendor token formats and skips `*.md`. A broadened scan of all 195 tracked files **and all 52 commits** found no credential, so there is nothing to disclose; the gap is prospective.
- `scripts/install.sh` creates `/opt/ttp` and `/var/lib/ttp` with bare `mkdir -p`. `install -d -m 0755 -o root -g root` would be idempotent and mode-setting; plain `umask 022` would not help, since `mkdir -p` does not touch an existing directory.
- `ttp bypass` accepts `SUDO_UID=0`. Only root can produce that value, so no boundary is crossed, but rejecting it would make the docstring literally true.
- `ControlSocketsGroupWritable 1` and `CookieAuthFileGroupReadable 1` in the generated torrc grant nothing today — `/run/tor/ttp` is 0700 — but they are latent: Tor's control protocol has no per-command ACL, so any future relaxation of that directory would convert them straight into full control-port authority.

## Method notes

Two questions were settled by reading what ships on the machine rather than by running it:

- **Does `systemd-run --scope` drop supplementary groups?** `systemd.scope(5)` defines no `User=`, so `systemd.exec(5)`'s implicit `initgroups` does not apply; and `systemd-run`'s entire 198-symbol import table contains `setresuid`/`setresgid` but no `setgroups` or `initgroups`. It does not.
- **Does `nft` treat each argv element as one token?** `main()` sums the argument lengths, allocates one buffer, concatenates the elements separated by a space, and calls `nft_run_cmd_from_buffer()` — which shares its parser with `nft -f`. It does not: a newline inside one argument starts another command.

The full machine-readable records, including every verifier's evidence and reasoning, are kept outside this repository with the audit run.
